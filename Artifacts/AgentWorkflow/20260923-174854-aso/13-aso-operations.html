3. 最高优先级发现

优先级问题建议
P0关键词字符预算按“字符”记录，但 Apple 限制是 100 bytes。1.38 的 zh-Hans 为 169 bytes、zh-Hant 为 169 bytes、ja 为 171 bytes、ko 为 141 bytes、ru 为 167 bytes。下一次 metadata 更新前，逐 locale 按 UTF-8 byte 计算；先换成报告第 5 节的候选词。不要直接把当前 1.20/1.38 keywords 原样上传。
P01.39 metadata 不完整。它不包含 subtitle、keywords、description，无法从仓库复现这次 listing 的完整输入。批准文案后，为 1.39/目标版本补齐每个实际维护 locale 的字段；上传前先与 App Store Connect 当前值做只读对照，避免把旧字段状态当成已更新。
P1公开页面类别是“工具”，而 Xcode 的 application category 是 Sports；商店类别不是由 Xcode build setting 自动证明的。在 App Store Connect 只读确认 primary category。若实际仍是 Utilities，评估把 Sports 设为 primary；这需要单独确认和审核，不在本次执行。
P1描述开头重复两遍“快速记录篮球比赛数据”，浪费首屏；英文描述使用“Basketball Journey”，但公开名称是 Basketball Journal。把首屏改成一句核心价值 + 一句差异化能力；统一产品称呼。Apple 说明描述第一句最重要。
P1营销首页仍写“即将上架 App Store”，会削弱已上架 App 的可信度；本地 support/privacy 与公开 listing 的名称也存在“篮球生涯”/“篮球生涯手帐”差异。更新 Pages 源文件与部署页面的状态、名称和 CTA；这属于独立页面发布动作，本次只提出，不执行。
P1仓库没有 Fastlane screenshots/preview 资产，无法审核当前截图顺序和首屏转化。先补齐截图证据；第一屏突出实时记分，第二屏语音记分，第三屏球员/球队统计，第四屏 AI 复盘，第五屏蓝牙协同，第六屏 Excel 批量导出。

6. 文案与截图方案

描述首屏

建议每个 locale 的前两句都回答“给谁、解决什么、为什么现在下载”，不要重复标题或把 Terms/Privacy 链接放在首屏。简体中文候选：

实时记录篮球比赛，自动汇总比分、球员技术统计和球队数据。支持语音记分、AI 赛后复盘、蓝牙协同与 Excel 导出，适合训练赛、野球局和业余联赛。

后续按功能顺序：实时记分 → 语音记分 → 球员/球队统计 → AI 总结/MVP → 蓝牙协同 → Excel 导出 → iCloud/导入导出。China locale 的 AI provider 只写 DeepSeek 或“AI 服务”，不要继续使用与项目规则不一致的 OpenAI/Anthropic 表述。

截图顺序

  1. 实时记分：一眼展示比分和完整技术统计。
  2. 语音记分：按住麦克风说出“球员 + 动作”，突出解放双手。
  3. 球员/球队数据：累计、场均、胜率、位置和比赛历史。
  4. AI 赛后复盘：总结、MVP、高光时刻；明确 Pro 或使用条件。
  5. 蓝牙协同：多人、多设备实时同步。
  6. Excel 批量导出：多场比赛打包 ZIP，突出新版本价值。

7. 验证计划

  1. 先在 App Store Connect 只读确认每个 locale 的真实 name/subtitle/keywords/description、primary category 和截图版本。
  2. 以本报告候选词建立固定 keyword-set；发布前对所有关键词做 100-byte 校验，并让对应语言母语者校审自然度。
  3. 发布后用相同 storefront、locale、keyword-set、app-id 和 provider 做 validation 快照；至少等待一个稳定观察窗口，不用一次搜索归因下载增长。
  4. 使用 App Analytics 分拆 Product Page Views、App Units、转化率和 locale；若能使用 Product Page Optimization，为“语音记分”与“AI/统计”卖点做截图实验。
  5. 每次只改变一组变量，记录版本、日期、locale、关键词集合、截图版本和转化变化；不要同时改名、类别、subtitle、keywords 和截图后再判断效果。

8. 未验证与不执行项
